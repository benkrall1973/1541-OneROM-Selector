# 1541 OneROM Selector v1.1.0 Performance and Simplification Deep Dive

## Executive conclusion

OneROM v0.7.2 does not accelerate the C64's initial PRG transfer from a physical
1541. The selector cannot use RBCP until enough C64-side code has loaded to
communicate with OneROM, so ordinary IEC loading remains the first bottleneck.
The current T1.1.0-21 PRG is 22,659 bytes, versus 18,963 bytes for v1.0.0.
Reducing the production PRG is therefore the most direct compatibility-friendly
way to improve physical-disk launch time.

The upgrade still creates substantial opportunities. Host-control v0.1.3 on
firmware v0.7.2 implements RBCP v0.1.2, including `GET_BOOT_SLOT_INFO`,
`LOAD_AND_EXIT`, `EXIT_CMD_RESP_RESTORE`, and corrected silent terminal-command
semantics.^1 The production selector can replace experimental cleanup code with
these stable operations, remove most diagnostics, consolidate metadata reads,
and pack the remaining 1541 machine code efficiently.

The expected work is materially easier than the original v1.0 implementation.
The communication architecture, device discovery, menu, NV persistence, ROM
switching, and universal bootloader already exist. The remaining work is a
bounded correctness fix followed by measured refactoring.

## Immediate Q=Quit finding

The official host-control v0.1.3 changelog states that
`GET_BOOT_SLOT_INFO` reports both the flash slot from which OneROM booted and
the RAM slot into which it was loaded, and explicitly says that this is what a
host needs to name in `LOAD_AND_EXIT`.^1 The plugin records that pair once at
startup and intentionally does not change it after later loads.^2

T1.1.0-21 proved that the overall terminal-command approach can work: it
returned the C64 to BASIC `READY.`, changed ROMs successfully, and permitted an
immediate physical-disk directory read on the first run. However, its Q path
uses the currently reported RAM slot as the `LOAD_AND_EXIT` destination. On a
second run, that query has returned `255`, and the selector's safety check has
correctly refused to transmit.

The next test should therefore be based on the documented boot pair, not a
guessed fallback:

1. Enter a fresh RBCP command-response session.
2. Confirm protocol v0.1.2 or later.
3. Call `GET_BOOT_SLOT_INFO`.
4. Validate that neither returned slot is `0xFF` (unknown), `0xAA` (reserved),
   or outside its reported range.
5. Pass the returned boot RAM and boot flash values directly to
   `LOAD_AND_EXIT`.
6. Do not poll or write an RBCP response header afterward; `LOAD_AND_EXIT` is a
   silent terminal command.^3
7. Restore only the C64's local KERNAL channel state and return to BASIC.

This is the strongest candidate for resolving the second-run issue. It should
still be treated as a hardware test until it passes repeated first-run,
second-run, unchanged-ROM, and changed-ROM scenarios.

`EXIT_CMD_RESP_RESTORE` is a second legitimate option. It lets a host supply up
to eight original bytes to repair the start of the displaced back-channel
region while exiting.^1 It may eventually offer a smaller quit implementation,
but only if the selector can reliably capture the original bytes before entry.
`LOAD_AND_EXIT` remains the safer next step because v0.7.2 explicitly provides
the boot pair for it.

## Where the current size goes

The current test build contains 379 BASIC lines and a 22,659-byte tokenized
PRG. A source-level inventory provides a useful directional breakdown:

| Area | Approximate source bytes | Observation |
|---|---:|---|
| Startup and initial service upload | 14,419 | Largest area; dominated by repeated `M-W` payload construction |
| Q=Quit diagnostics | 5,397 | Test-only code that should not survive into production |
| Menu | 3,468 | Includes display and navigation |
| UI and device selection | 3,013 | Polling, device selection and shared display helpers |
| Service/helper routines | 3,554 | Additional drive-side payloads and access helpers |
| Save/edit path | 1,696 | Direct editing code only; related NV/name logic also appears elsewhere |

These are source-text measurements, not exact tokenized-PRG attribution, but
they correctly identify the main targets. T21 contains approximately 95 BASIC
lines that issue `M-W`. Machine-code payload bytes are represented through long
sequences such as `CHR$(169)+CHR$(...)`; that representation occupies far more
space in the PRG than the raw machine code itself.

## Optimization opportunities

### 1. Remove test diagnostics from the production branch

This is the lowest-risk first reduction. T16-T21 should remain as historical
hardware tests, while the next production-oriented build should retain only:

- concise startup status;
- actionable errors;
- the proven Q cleanup path;
- optional diagnostic codes small enough to photograph.

The large mapping screen, protocol narration, checkpoint prompts, and test-only
branches should not be carried into v1.1.0. Removing them should recover much
of the approximately 3.7 KB increase from v1.0.0 to T21.

### 2. Pack the 1541 machine-code service as binary

This is likely the largest single size improvement. The raw service is roughly
720 bytes, but its BASIC `CHR$()` representation expands every byte into
multiple characters, parentheses, operators, and repeated `M-W` scaffolding.

Recommended implementation:

- append a compact binary payload to the PRG;
- run a very small loader before BASIC allocates variables over that area;
- send the payload to the drive in the largest safe `M-W` chunks;
- retain a checksum or fixed build-time length so corrupt packaging is caught.

A simpler interim option is packed hexadecimal or a denser DATA encoding. It
will be smaller than hundreds of `CHR$()` expressions but slower to decode and
larger than raw binary. The raw appended payload is the preferred production
design if VICE and hardware loading both validate it.

This change improves physical-disk launch because fewer bytes cross IEC. It can
also reduce BASIC parsing and string-allocation overhead during startup.

### 3. Determine which custom service routines RBCP v0.1.2 replaces

The host-control plugin is designed to be driven by the retro system's CPU and
the upstream project supplies reference 6502 host implementations.^4 Firmware
v0.7.2 does not provide a magic C64-callable selector or automatically inject
the host code into 1541 RAM. Some host-side machinery therefore remains
necessary.

Nevertheless, custom routines should be audited command by command. Stable
RBCP v0.1.2 provides standard operations for:

- protocol and device information;
- RAM- and flash-slot enumeration;
- slot load and switch;
- NV capability, read and transactional write;
- boot-slot discovery;
- clean terminal exit and restoration;
- optional pipes, auxiliary I/O and LED control.^1

Any custom code duplicating those semantics should be removed. Code whose job
is merely transporting RBCP over the 1541/C64 path will remain, but it should
be consolidated into one reusable resident service instead of repeated
operation-specific payloads.

### 4. Use a single discovery/population pass

The present startup displays ROMs found and then transitions to a separately
rendered menu. The display transition itself is not the primary disk-loading
bottleneck, but duplicate metadata or saved-name reads would waste IEC time
after the PRG has loaded.

The production flow should be:

1. Poll and select the IEC device.
2. Locate OneROM in the applicable socket.
3. Enter one RBCP session.
4. Read slot count, active selection, labels and saved-name state once.
5. Populate the in-memory menu arrays during that same pass.
6. Render the menu directly.

The program can still show `FOUND n ROMS` briefly if desired, but it should do
so from already populated arrays rather than initiating another query. Removing
fixed cosmetic waits will improve perceived speed without affecting protocol
safety.

### 5. Remove or demote in-selector ROM renaming

For a small, dependable selector, removing editing is the recommended default.
OneROM already provides configured ROM labels, and multi-ROM display labels
come from `chips[0]`. The CLI also manages programmed slot configurations and
images.^5 Most users are likely to name ROMs when preparing their OneROM rather
than repeatedly editing names on a C64.

Benefits of removing `E=EDIT` and custom-name persistence include:

- smaller PRG and faster physical-disk load;
- fewer strings and less BASIC heap pressure;
- fewer NV transactions and failure states;
- simpler menu and instructions;
- less dependence on a private name-storage layout.

The cost is convenience for users who want to rename slots without returning
to a modern computer. A reasonable compromise is a lean primary selector and a
separate optional `OneROM Name Editor` utility. This keeps the frequently used
selector fast while preserving the feature for users who value it.

### 6. Retain the universal bootloader for v1.1.0

The universal bootloader and selector solve different lifecycle problems. The
selector changes or saves a choice while the system is running. The bootloader
applies the saved choice when the physical 1541 starts. RBCP v0.1.2 adds better
runtime control but does not, by itself, replace this project-specific saved
selection policy.

Pulling the 720-byte service from the bootloader is not an obvious win:

- after the bootloader hands over to the selected DOS image, its ROM bytes may
  no longer be the active bytes visible to the 6502;
- permanently reserving approximately 720 bytes of the 1541's limited RAM is a
  significant compatibility risk;
- fetching service bytes through RBCP still requires working host-side RBCP
  transport code and may simply move, rather than remove, the dependency;
- coupling the selector to a particular bootloader revision would reduce its
  ability to work with otherwise compatible OneROM configurations.

The bootloader should remain unchanged until a memory map proves a safe
resident region and measurements show a worthwhile benefit. Packing the
service inside the C64 PRG is safer and benefits every compatible installation.

### 7. Treat a fastloader as optional

A fastloader could dramatically reduce load time from a stock physical 1541,
but it introduces compatibility questions involving device numbers, alternate
DOS ROMs, JiffyDOS, emulators, modern IEC devices and chained hardware. It also
adds code that works against the goal of a smaller universal selector.

The baseline release should remain standard-KERNAL-load compatible. A separate
fast-load disk edition can be evaluated only after the lean PRG size is known.
Reducing transferred bytes benefits every loader and should come first.

## Recommended implementation sequence

### Phase 1 — Finish correctness

Build one focused Q diagnostic using the exact boot RAM/flash pair returned by
`GET_BOOT_SLOT_INFO`. Test:

- Q immediately after a physical drive start;
- a second selector run without resetting anything;
- Q after changing the highlighted choice but without saving;
- save/switch followed by another selector run;
- devices 8 and 9 where practical;
- two immediate physical-directory reads after every successful exit.

Do not optimize or remove diagnostic evidence until this matrix passes.

### Phase 2 — Establish size and timing baselines

Record for v1.0.0, T21 and the first clean production candidate:

- PRG byte size;
- physical 1541 load time from command to `READY`/RUN;
- startup time after RUN to menu;
- number of `M-W` transactions;
- time for Q and save/switch;
- free BASIC memory at the menu.

Measurements should be repeated at least three times because physical-drive
seek position and disk layout affect timing.

### Phase 3 — Produce the lean selector

In this order:

1. Remove T16-T21 diagnostic UI from the production source.
2. Remove fixed presentation delays and render from populated arrays.
3. Remove name editing from the primary selector, preserving configured labels.
4. Consolidate repeated query and upload helpers.
5. Pack the remaining machine-code service as raw binary.
6. Re-tokenize, validate and compare physical load/startup timings after each
   meaningful change.

Each change should retain the existing layout and colors initially, matching
the project's established test strategy.

### Phase 4 — Optional features

Only after the lean baseline is hardware-proven:

- separate name-editor utility;
- optional fastloader edition;
- LED progress using the v0.7.2 LEDs group;
- USB logging through RBCP Pipes for diagnostics rather than production UI;
- further assembly conversion if BASIC execution, rather than disk transfer,
  becomes the measured bottleneck.

## Expected outcome

The project should be able to return near or below the v1.0.0 PRG size despite
adding clean Q=Quit. A more aggressive binary-payload conversion may reduce it
substantially further. An exact target should not be promised until the
machine-code payload is extracted and the production diagnostics are removed,
but a several-kilobyte reduction is realistic.

The optimization work should indeed be easier than the original selector. It
is mostly subtraction, consolidation and packaging around a now-working
architecture. The main rule is to finish the boot-pair Q fix first and preserve
T21 as the known hardware baseline throughout the refactor.
